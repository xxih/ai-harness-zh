# NEXUS 模式说明

## 目标

解释 `agency-agents` 中 `NEXUS-Full`、`NEXUS-Sprint`、`NEXUS-Micro` 三种模式到底是什么意思，它们分别解决什么问题，以及为什么说这种写法适合作为“如何启动一套编排流程”的参考。

## 先说结论

这三个模式本质上不是三套完全不同的方法论，而是同一套多 agent 编排框架在三种任务粒度下的启动模板：

- `NEXUS-Full`：整项目级
- `NEXUS-Sprint`：功能 / MVP 级
- `NEXUS-Micro`：单任务 / 单问题级

也可以理解为，它先替用户回答了一个最容易卡住的问题：

> “我现在这个任务，到底该拉多少角色、走多长流程、在哪些地方设质量门禁？”

`agency-agents` 没让用户自己从 100 多个 agent 里临场拼流程，而是先把常见工作规模抽象成三档预设模式。用户先选模式，再填任务内容。

## 它到底在抽象什么

在普通的 agent 仓库里，用户经常只拿到一堆角色名：

- Frontend Developer
- Backend Architect
- UX Researcher
- Reality Checker
- Growth Hacker

但真正难的不是“知道有哪些角色”，而是：

1. 什么时候该用哪些角色
2. 这些角色是并行还是串行
3. 哪一步必须 review / verify
4. 做一个 bugfix 和做一个完整产品，流程显然不能一样长

`NEXUS-Full / Sprint / Micro` 的作用，就是把这些问题预先打包成三种流程规模。

所以它抽象的不是“领域”，而是“任务规模 + 协作复杂度 + 质量门禁强度”。

## 三种模式分别是什么意思

## `NEXUS-Full`

### 它对应什么任务

适合“从零开始做一个完整项目”。

典型场景：

- 做一个完整产品
- 从 discovery 一直走到 launch / operate
- 需要市场、设计、工程、测试、运营多角色协作

在 `agency-agents` 的 quick start 里，这个模式默认覆盖 7 个阶段：

1. `Phase 0: Discovery`
2. `Phase 1: Strategy`
3. `Phase 2: Foundation`
4. `Phase 3: Build`
5. `Phase 4: Harden`
6. `Phase 5: Launch`
7. `Phase 6: Operate`

### 它的核心含义

意思不是“把所有 agent 都叫出来干活”，而是：

- 任务本身足够大，需要跨多个职能阶段
- 不只是实现，还包括前置研究、策略、上线和后续运维
- 编排者要负责阶段切换和质量门禁

换句话说，`Full` 是“完整生命周期 pipeline”。

### 为什么它重要

很多多 agent 流程写法最大的问题是只覆盖“实现阶段”。

但真实项目里，失败往往发生在：

- 前期没做 discovery
- 架构与设计没对齐
- 实现完没有 hardening
- 上线后没有 operate 视角

`NEXUS-Full` 的价值，就是把这些阶段也纳入编排，而不是只写“开发怎么做”。

## `NEXUS-Sprint`

### 它对应什么任务

适合“做一个功能、一个 MVP，或者一个有限范围的交付”。

典型场景：

- 已经有产品方向，不需要重新做完整 discovery
- 需要 2 到 6 周内交付一个 feature 或 MVP
- 还是要多角色协作，但规模明显小于完整项目

在 quick start 里，它默认：

- 跳过 `Phase 0`
- 从 `Phase 1` 的架构与 sprint planning 开始
- 保留 Dev↔QA loop
- 保留最后的 `Reality Checker` 门禁

### 它的核心含义

`Sprint` 不是弱化版 `Full`，而是“明确裁掉不必要阶段后的中等流程模板”。

它表达的是：

- 市场是否成立，已经基本知道了
- 现在重点是把需求变成可交付产物
- 仍然需要 PM / Design / Eng / QA 协作
- 但不值得启动一个完整的企业级 pipeline

所以它是“有限生命周期 pipeline”。

### 为什么它常常是最有用的

真实日常开发里，大部分任务都不是：

- 小到只修一个点
- 也不是大到从市场研究一路做到运营

很多任务恰好就是：

- 做一个 feature
- 搭一个 MVP
- 交一个版本

这时如果没有 `Sprint` 这种中档模式，用户很容易在两个极端里摇摆：

- 要么流程太重，动不动就上完整编排
- 要么流程太轻，直接让一个 agent 开干，缺少中间的架构和 QA

`NEXUS-Sprint` 解决的正是这个问题。

## `NEXUS-Micro`

### 它对应什么任务

适合“一个具体问题、一段有限工作流、一个目标明确的小任务”。

典型场景：

- 修一个 bug
- 做一次性能诊断
- 跑一轮合规审计
- 做一次市场调研
- 优化一段 UX

### 它的核心含义

`Micro` 不是不要编排，而是把编排压缩成一个很短的角色链路。

例如它给出的 bugfix 例子是：

- `Backend Architect` 调查并修复
- `API Tester` 验证修复
- `Evidence Collector` 确认没有视觉回归

也就是说，`Micro` 依然有：

- 实施角色
- 验证角色
- 交付闭环

只是它不再需要完整 phase 结构。

### 为什么这个设计好

很多仓库一谈多 agent，就默认必须上复杂 orchestrator。

但现实里，大量任务其实只需要：

- 2 到 4 个角色
- 很短的顺序链路
- 一个最小的 verify gate

`NEXUS-Micro` 把这件事说清楚了：

> 多 agent 不等于大工程。小任务也可以有最小编排。

## 三种模式的真正共同点

表面上看，它们只是参与角色数量不同。

但更关键的共同点是三者都保留了同一套编排原则：

1. 有明确的 owner
2. 有阶段或顺序
3. 有 handoff
4. 有质量门禁
5. 有 evidence，而不是只靠口头完成宣称

也就是说，三种模式变的是“流程长度”，不变的是“编排纪律”。

这正是它们最值得参考的地方。

## 为什么说“用户入口非常直接”

这是这套设计最实用的地方之一。

普通 prompt 资产常见的问题是，用户得自己拼装启动方式：

- 先选 agent
- 再写任务描述
- 再自己补流程要求
- 再补 QA 要求
- 再决定是否需要 handoff

而 `NEXUS` 的 quick start 把入口改成了：

1. 先选模式
2. 再填任务信息
3. 然后直接复制一段启动 prompt

例如：

- `Activate Agents Orchestrator in NEXUS-Full mode`
- `Activate Agents Orchestrator in NEXUS-Sprint mode`
- `Activate [SPECIFIC AGENT] for [TASK DESCRIPTION]`

这种写法直接的原因是：

- 它先把“流程规模”显式化了
- 它帮用户预选了需要的角色集合
- 它提前声明了质量门禁和 retry 规则
- 它把自由度压到“任务内容”，而不是“流程设计”

这对用户很友好，因为用户通常知道自己要做什么，但不一定知道多 agent 流程该怎么搭。

## 这对当前仓库意味着什么

当前仓库不适合照搬 `NEXUS` 名词体系，也不适合引入那么多角色。

但它有一个非常值得吸收的点：

> 不要只给“能力资产”，还要给“怎么启动这套能力”的入口模板。

换成当前仓库语境，就是：

- `agent-orchestration` 不只是讲原则
- 还可以考虑补“何时走重编排 / 轻编排 / 最小编排”的启动模板

例如未来完全可以有类似这样的三档理解，但不必沿用 NEXUS 命名：

- 重编排：研究 -> 计划 -> 实现 -> review -> verify
- 中编排：计划 -> 实现 -> verify
- 轻编排：实现 -> verify

这里真正值得借鉴的不是名字，而是“按任务规模提供预设启动入口”。

## 一个更直白的理解方式

如果要把这三种模式翻成更口语的话：

- `NEXUS-Full`
  - “这不是一个任务，这是一个项目。”
- `NEXUS-Sprint`
  - “这不是一个项目全生命周期，但也绝不是一个单点修补。”
- `NEXUS-Micro`
  - “这是个小任务，但仍然要有基本的实现和验证闭环。”

所以它们真正帮用户做的，是先回答：

- 这件事到底有多大？
- 要上多重的流程？
- 该不该启用 orchestrator？

## 对当前仓库的建议

如果后续要把这个思路吸收到当前仓库，建议只吸收下面三点：

1. 给 `agent-orchestration` 增加“按任务规模选择流程”的说明。
2. 给不同规模的任务准备最小启动模板，而不是只写抽象原则。
3. 保持当前仓库自己的 skill-first 结构，不把模式设计变成大量 agent roster。

不建议吸收的点：

1. 不需要复制 `NEXUS-Full / Sprint / Micro` 这些命名。
2. 不需要为每档模式强行绑定一大串固定角色。
3. 不需要把当前仓库做成一个完整的 multi-agent 平台说明书。

## 总结

`NEXUS-Full`、`NEXUS-Sprint`、`NEXUS-Micro` 的意义，不在于名字本身，而在于它把多 agent 编排从“自由拼装”变成了“按任务规模选预设流程”。

这件事的价值很大，因为它降低了用户启动复杂协作的门槛，也让同一仓库里的大任务、中任务、小任务都能共享一套编排纪律，而不是各写各的 prompt。
