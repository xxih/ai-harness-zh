# Review 阶段

## 目标

在关键节点引入第二视角，发现自己在实现时容易忽略的问题。

## 触发条件

- 关键任务完成后
- 准备提交 PR 或合并前
- 高风险改动后
- 用户明确触发 `/review`

## 最小流程

1. 读取需求或计划
2. 读取改动内容和相关测试
3. 先找阻塞问题
4. 再找重要改进项
5. 最后给出是否可继续

## 重点问题

- 改动是否符合原目标
- 是否缺错误处理、边界条件、回归保护
- 测试是否真的覆盖关键行为
- 是否有无关复杂度或意外副作用

## 结果格式

- `阻塞`
- `改进`
- `观察`
- `ready` / `not-ready`

## 不要做

- 用泛泛表扬替代问题判断
- 把可证伪的问题说成主观偏好
- 有阻塞项还宣布可继续
