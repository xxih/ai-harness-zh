# 规格说明：harness分层吸收与最小skill化

## 背景

当前仓库的目标是沉淀可复用的 AI prompt 资产，而 `references/repos/` 中的参考对象普遍是成熟但“大而全”的 harness。此次任务不以直接移植某个完整 harness 为目标，而是要先识别可拆分、可验证、可维护的最小吸收单元。

## 目标

本任务需要在研究结论基础上，直接提炼两类最小 coding 能力：

- 研究检索类：在写代码前，先搜索代码库、测试、外部实现与参考仓库
- 质量保障类：覆盖测试先行、变更验证、独立评审三个控制点，但不必一项对应一个 skill

## 交付范围

### 1. 参考仓库能力分类

需要将 `everything-claude-code`、`superpowers`、`oh-my-opencode` 按能力层拆分，而不是只按仓库维度做摘要。

成功标志：

- 存在一份可复用的分类文档，说明每个仓库更适合作为哪一层能力的来源。
- 分类文档明确区分“适合先吸收的能力”和“暂不吸收的能力”。

验收证据：

- `assets/reference-map.md`

### 2. 最小 skill 吸收原则

需要明确什么样的能力可以被当前仓库吸收为独立 skill，什么样的能力应继续保留为参考。

成功标志：

- 原则至少覆盖单一意图、工具无关性、可落盘产物、可评估性、与现有资产不重复这几个维度。
- 原则能直接指导后续新增 skill 的边界判断。

验收证据：

- `assets/reference-map.md`
- `outputs/2-plan.md`

### 3. 第一波最小能力落地

需要真正落地最小 coding 能力，而不是按参考仓库中的 skill 名称逐项复刻。

成功标志：

- 能明确区分“能力内核”和“参考来源”
- 质量保障相关的多个参考 skill 被抽象成清晰的阶段分工，而不是简单并列导入
- 后续新增 skill 应尽量覆盖一整条最小闭环，而不是只复制单一参考文件名
- 共享 skill 的默认入口文案必须面向用户场景、质量动作和交付判断，而不是把内部设计修正直接写成使用条件

验收证据：

- `assets/reference-map.md`
- `outputs/2-plan.md`
- `outputs/3-tasks.md`

### 4. 仓库同步更新

需要同步更新仓库内与新资产相关的说明和校验。

成功标志：

- README 按类别列出新增 skill
- `scripts/validate_assets.py` 能覆盖新增 skill 的最小约束
- 结构性变更后校验通过

验收证据：

- `README.md`
- `scripts/validate_assets.py`
- `python3 scripts/validate_assets.py`

## 非目标

- 直接复制任一参考仓库的完整目录结构、运行时机制或插件体系。
- 在本次任务中同时落地 prompt 资产治理、多 agent 编排、hooks 自动化、MCP 管理、多模型路由等重能力。
- 把参考仓库整理成泛泛而谈的读书笔记，而不形成可执行的吸收策略。

## 约束

- 新结论必须服务于当前仓库“沉淀可复用 prompt 资产”的目标。
- 默认保持中文文档表达，代码、路径、协议关键字保持原文。
- 后续真正新增或修改共享 skill 时，应优先补 eval，并在结构性变更后运行 `python3 scripts/validate_assets.py`。
- 共享 skill 的入口说明要写“用户何时该用、会得到什么”，不要写“作者为什么这样打包”。
