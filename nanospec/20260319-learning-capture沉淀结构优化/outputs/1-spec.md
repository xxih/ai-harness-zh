# 规格说明：learning-evolution 闭环优化

## 1. 背景

当前 `learning-capture` 的正式结构已经简化为两层：

- `rules.md`：长期规则候选
- `notes.md`：其他记录

这比早期的 `learnings / promote-candidates / project-rules` 三分法更轻，但真实使用里仍然暴露出一个核心问题：`notes.md` 的名字和边界都太泛，导致它既不像规则池，也不像资产孵化面，更不像任务证据面。写进去的内容常常“看起来有价值”，但后续动作不明确。

用户的最新判断是：

1. `rules` 的沉淀通常比较有用。
2. `notes` 的定位不清，需要重新定义，甚至可能取消。
3. learning 不应该只会记规则，还要更强地支持 skill：当某类流程在真实任务里反复出现时，应能留下足够证据，帮助后续把它沉淀成 skill。
4. 可以借鉴 Claudeception 对“可复用知识提炼”的敏感度与 hooks 提醒思路，但不能简单照搬“所有东西都沉淀成 skill，并直接启用”的模式。

## 2. 本次要回答的问题

### 2.1 `notes.md` 的去留与职责

需要明确回答：

- `notes.md` 是否保留。
- 若保留，它是“普通杂记”、 “候选资产草稿”、 “证据池”，还是别的东西。
- 若不保留，`rules` 之外的经验应落到哪里。

### 2.2 learning 对 skill 的支撑结构

需要明确：

- 什么信号说明一类工作已经接近 skill 候选，而不只是一次性经验。
- 应该保留哪些材料，才能支持后续创建 / 改写 skill。
- 这些材料应该如何组织，避免再次退化成模糊 notes。

### 2.3 hooks 的吸收边界

需要明确：

- 哪些 hooks 启发值得吸收：提醒触发、候选识别、回顾时机。
- 哪些做法不吸收：自动创建 skill、自动发布正式资产、重依赖观察运行时。
- 若未来要支持 hooks，应只作为 target 层增强，而不是学习主流程前提。

### 2.4 研究先行的范围收敛

在用户最新要求下，本轮需要先完成研究，再谈结构改造。也就是说，本轮不再直接回答“第二层文件叫啥”，而是先回答：

- `ECC learning v2` 到底在解决什么问题。
- `Homunculus` 的 instinct / evolve 路线为什么成立，风险又在哪里。
- 业界持续学习方法论除了 hooks + memory 之外，还有哪些可借的路径。
- 对当前仓库来说，哪些属于“现在就能吸收的方法论”，哪些只是远期参考。

## 3. 当前问题拆解

### 3.1 `rules.md` 为什么更稳定

`rules.md` 天然更容易有价值，因为它同时具备：

- 来源明确：通常来自用户显式纠正。
- 作用范围明确：项目级 / 团队级 / 分发级。
- 落点明确：`AGENTS.md`、README、某个 skill、某个 eval。
- 下一步明确：保留候选、提议回写或丢弃。

也就是说，`rules` 记录的不只是“发生了什么”，而是“以后默认该怎么做”。

### 3.2 `notes.md` 为什么让人摸不着头脑

当前 `notes.md` 至少混杂了三种不同东西：

1. 局部经验：这次遇到某个问题时做了什么。
2. 流程雏形：某条工作流看起来值得沉淀成 skill。
3. 研究结论：某个方向的对照、取舍或架构判断。

它们的共同问题是：

- 粒度不一致。
- 作用范围不一致。
- 后续动作不一致。
- 标题叫 `notes`，很难让人一眼知道“这是给谁看的，之后怎么用”。

结果就是：记录可以写出来，但很难自然推进到 skill / command / doc / eval 等正式资产。

### 3.3 现有 learning 对 skill 的支持为什么偏弱

当前结构强调“先记录，暂不自动升级”，这个方向本身没问题；问题在于：

- 记录的内容不足以支撑后续 skill 编写。
- 没有明确识别“重复流程”或“强 workflow 模式”的入口。
- 缺少一种稳定格式来保存 skill 所需的原料，例如：
  - 触发场景
  - 输入材料
  - 关键步骤
  - 产出形态
  - 不适用边界
  - 已验证样例
  - 相关证据

所以现在的 learning 更像“留档”，不像“为未来资产化预备材料”。

## 4. 目标

### 4.1 明确两层沉淀的职责

优化后的 learning-capture 至少要让人能清楚区分：

- 哪类内容应该进 `rules`
- 哪类内容属于规则之外，但仍值得长期保留
- 这些“规则之外的东西”保存后下一步通向哪里

### 4.2 让规则之外的记录变成“资产支撑面”而不是杂记

无论最终名字是否仍叫 `notes.md`，都应把它收敛成更明确的类型，例如：

- skill 候选证据
- workflow 碎片
- 重复任务信号
- 待资产化的样例 / 验证线索

关键要求不是“字段更多”，而是“记完之后知道它支持什么”。

### 4.3 为 skill 提供非自动化但可执行的支撑

本轮不要求自动生成 skill，但要让 learning-capture 能稳定积累下列材料：

- 某项工作已重复出现的证据
- 典型触发语或触发场景
- 输入 / 输出样例
- 步骤骨架
- 已验证结果或验收线索
- 应该并入现有 skill 还是新建 skill 的初步判断

### 4.4 给 hooks 留出可选增强接口

应允许未来在 target 层增加“提醒型 hooks”，例如：

- 会话结束时提醒是否需要 capture
- 重复任务信号达到阈值时提醒复盘

但这些只能生成提醒或候选，不能直接替代人工判断与正式资产编写。

### 4.5 明确 learning-evolution 的两阶段动作

`learning-evolution` 需要显式分成两阶段：

- 第一阶段：`Observation -> Selection -> Representation`
- 第二阶段：`Evolution`

其中第一阶段是默认动作；第二阶段只有在用户明确给出 `evolution`、演化、收敛正式资产、继续 codify 这类指令时才触发。不能因为已经有 observation、hooks、候选或 support 卡片，就自动跳到第二阶段。

### 4.6 范围边界

本轮只更新 `learning-evolution` 相关正式资产与其 target 镜像，不覆盖 `spec-driven`、`nanospec` 等邻近 skill。

### 4.7 正文可执行性

`learning-evolution` 的正式 skill 正文必须让 AI 快速读懂以下问题，不能继续停留在概念堆叠状态：

- 什么时候应该调用这个 skill
- 每条信号最后会落到哪个出口
- 哪些属于默认动作，哪些只有明确指令下才执行
- 应该读哪些输入、写到哪些位置
- 遇到任务范围变化时如何回写对齐

### 4.8 正文独立性

`learning-evolution` 作为普通 learning skill，其 prompt 正文默认必须保持独立：

- 不主动引用 `nanospec`、`spec-driven` 之外的其他 skill 或 command
- 不把任务容器、`alignment.md`、`align` 或某个协作机制写成默认前提
- 如果当前环境确实已有既定工作面，只能写成泛化表述，例如“回写到现有记录位置”或“同步受影响工作文件”

## 5. 备选方向

### 方向 A：保留 `notes.md`，但重命名 / 重定义

思路：保留规则之外的单文件入口，但把它明确成“资产支撑面”，例如 `candidates.md`、`signals.md`、`skill-support.md` 等。

优点：

- 延续当前两层结构，迁移成本低。
- 比 `notes` 更容易表达用途。

风险：

- 如果边界写得不够硬，仍可能退化成杂记。

### 方向 B：取消统一 `notes.md`，改成面向用途的记录类型

思路：`rules.md` 保留；规则之外不再统一叫 notes，而拆成更明确的类型，例如：

- `skill-signals.md`
- `workflow-fragments.md`
- `research-notes.md`

优点：

- 含义更明确。
- 后续动作与使用者更清楚。

风险：

- 结构可能变重。
- 手工触发门槛变高，重新回到“分类过多”的老问题。

### 方向 C：保留 `rules.md`，其余默认回写到任务容器；`.learned/` 只保留跨任务候选

思路：把普通局部经验尽量留在任务容器；`.learned/` 只接收跨任务、跨会话仍值得保留的候选资产支撑材料。

优点：

- 降低 `.learned/` 杂质。
- 更符合“学习”应偏长期的直觉。

风险：

- 需要更明确的“何时提升到 `.learned/`”判断门。

## 6. 推荐判断标准

无论采用哪种结构，规则之外的记录都至少应满足下面四个问题里的两个以上：

1. 未来还会重复遇到吗？
2. 它是否支持某个 skill / command / eval / doc 的创建或改写？
3. 它是否包含不显然、靠试错或真实执行得来的信息？
4. 它是否已经具备具体证据，而不是纯想法？

如果四项都答不上来，就不应该进入长期 learning。

## 7. 本次任务的完成标志

满足以下条件即可视为本轮规格清晰：

1. 形成对 `ECC learning v2`、`Homunculus` 与行业方法论的研究结论，并落盘到任务容器。
2. 在此基础上将包正式改名为 `learning-evolution`，把“只记录”升级为“信号 -> 判断 -> 分流 -> codify”的闭环。
3. 将长期候选从 `.learned/notes.md` 重构为 `.learned/support.md`，并明确 task-local 与 long-term 的分层。
4. 保留未来接入 hooks / observer 的自动化接口，但当前 source 资产仍保持工具无关、文件驱动。
5. `learning-evolution` 正文明确两阶段动作，并把 `Evolution` 改成显式指令触发。
