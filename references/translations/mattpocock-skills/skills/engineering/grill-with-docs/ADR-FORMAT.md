# ADR 格式

> 原文:[ADR-FORMAT.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/grill-with-docs/ADR-FORMAT.md)

ADR 放在 `docs/adr/`,按顺序编号:`0001-slug.md`、`0002-slug.md`,以此类推。

**懒加载创建 `docs/adr/` 目录**——第一份 ADR 需要时再建。

## 模板

```md
# {决策的短标题}

{1-3 句话:背景是什么、我们决定了什么、为什么。}
```

就这么多。**一份 ADR 可以只有一段话**。价值在于记录"我们做了一个决定 + 为什么",**不在于把表单字段填满**。

## 可选小节

只在它们真的带来价值时才加。大多数 ADR 不需要。

- **Status** frontmatter(`proposed | accepted | deprecated | superseded by ADR-NNNN`)—— 决策被重访时有用
- **Considered Options(候选项)** —— 只在被否决的备选值得被记住时写
- **Consequences(后果)** —— 只在非显而易见的下游影响需要点出时写

## 编号

扫一下 `docs/adr/`,找最大编号 +1。

## 何时该提议 ADR

下面三个条件**必须全部**成立:

1. **难以回滚** —— 改主意的代价是实质的
2. **没上下文就难以理解** —— 未来读者看着代码会想"他们当时图啥?"
3. **是真权衡的结果** —— 当时有真正的备选,你出于具体理由选了一个

如果决策容易回滚,跳过——反正你会回滚。如果不会让人意外,没人会问为啥。如果根本没有备选,记录"我们做了显而易见的事"也没意义。

### 什么算

- **架构形状**。"我们用 monorepo。" "写模型是事件溯源,读模型投射到 Postgres。"
- **跨 context 的集成模式**。"Ordering 和 Billing 通过领域事件通信,不走同步 HTTP。"
- **带锁定效应的技术选型**。数据库、消息总线、auth provider、部署目标。**不是每个库都要记**——只记那些换掉要花一个季度的。
- **边界和范围决策**。"Customer 数据由 Customer context 拥有,其它 context 只能用 ID 引用。" "明确不做"和"明确做"一样有价值。
- **故意偏离常规路径**。"我们用手写 SQL 不用 ORM,因为 X。" 任何"合理读者会以为是反过来"的决策都该记——这能阻止下一个工程师"修复"一个故意设计的东西。
- **代码看不到的约束**。"合规要求,我们不能用 AWS。" "响应必须 <200ms,合作伙伴 API 合同要求。"
- **被否决的备选,如果否决理由不显然**。如果你考虑了 GraphQL 选了 REST 出于微妙原因,记下来——否则六个月后又有人提 GraphQL。
