# 逻辑原型

> 原文:[LOGIC.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/prototype/LOGIC.md)

一个**小的交互式 terminal app**,让用户**手动驱动状态模型**。当问题是**业务逻辑、状态转移、或数据形状**时用——这类东西纸上看着合理,但推过真实 case 才能感觉到哪里不对。

## 什么时候是对的形状

- "我不确定这个状态机能不能处理'先 X 后 Y'的边界。"
- "这个数据模型真的能表达 X 这种情况吗?"
- "想在写之前对 API 长啥样有个感觉。"
- 任何用户想**按按钮、看状态变**的场景。

如果问题是"它该长啥样"——**错分支**,用 [UI.md](UI.md)。

## 流程

### 1. 把问题说清楚

写代码之前,**写下你在原型化的是什么状态模型 + 什么问题**。一段话,放原型 README 或文件顶端注释。**回答错问题的逻辑原型就是纯浪费**——让问题外显,这样以后能验,不管用户当场在还是 AFK 回来看。

### 2. 挑语言

用宿主项目用的语言。如果项目没有明显的运行时(比如纯文档仓库),问一下。

**匹配项目已有工具约定**——别为原型加新的 package manager 或 runtime。

### 3. 把逻辑隔离到一个可移植模块里

把**回答问题的那段逻辑**放到一个**小、纯**的接口背后,**以后能整块抬出来扔进真代码库**。**它周围的 TUI 是一次性的;逻辑模块不是**。

形状要看问题:

- **纯 reducer** —— `(state, action) => state`。动作是离散事件、状态是单一值时好用。
- **状态机** —— 显式状态 + 显式转移。"当前哪些动作合法"本身就是问题时好用。
- **一小组纯函数**作用于平铺数据类型。没有隐式"当前状态"——只是变换——时好用。
- **类或带清晰方法面的模块**,当逻辑真的拥有持续的内部状态。

**挑最适合问题的形状,不是最容易接 TUI 的**。**保持纯**:无 I/O,无 terminal 代码,无 `console.log` 当控制流。**TUI 进口它,调用它;反方向什么都不能流**。

这就是原型为什么有生命周期之外价值。问题被回答后,验证过的 reducer / 机器 / 函数集可以**抬进真模块**——TUI 外壳删掉。

### 4. 构最小 TUI 来暴露状态

构造为**轻量 TUI** —— 每 tick 清屏(`console.clear()` / `print("\033[2J\033[H")` / 等价物),重渲染整帧。**用户应该总是看到一个稳定视图,不是越长越长的回滚**。

每帧两部分,按顺序:

1. **当前状态**,美化打印且 diff 友好(每字段一行,或格式化 JSON)。用**粗体**标字段名/小节,**变暗**标不太重要的上下文(时间戳、ID、派生值)。原生 ANSI 转义就够——`\x1b[1m` 粗体,`\x1b[2m` 变暗,`\x1b[0m` 重置。**项目已经在用样式库**就用,否则别拉新依赖。
2. **键盘快捷键**列在底部:`[a] add user  [d] delete user  [t] tick clock  [q] quit`。键加粗,描述变暗,或反过来——哪种好读用哪种。

行为:

1. **初始化状态** —— 一个内存对象/结构。启动时渲染第一帧。
2. **一次读一个按键**(或一行),派发给改状态的 handler。
3. **每次动作后重渲染整帧** —— 别追加,要替换。
4. **循环到退出**。

**整帧应在一屏内**。

### 5. 一条命令跑起来

加一个脚本到项目已有的任务跑法(`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`)。用户跑 `pnpm run <prototype-name>` 或等价物——**永远不该需要记一条路径**。

宿主项目没有任务跑法的话,把命令放在原型 README 顶部就行。

### 6. 交给用户

把跑命令给用户。**他们自己驱动**;有趣的时刻是他们说"等等,这不该可能"或"咦,我以为 X 是反过来的"——那些是**点子里的 bug**,这才是整件事的重点。如果他们想加新动作,加。**原型会进化**。

### 7. 抓取答案

原型干完它的活,**问题的答案是唯一值得留的东西**。用户在 → 问他们学到啥。不在 → 在原型旁留 `NOTES.md`,等以后填(或者你看了 session 后填),然后再删原型。

## 反模式

- **别加测试**。需要测试的原型就不再是原型。
- **别接真数据库**。用内存存储,除非问题就是关于持久化。
- **别泛化**。不要"以后可能要支持 X 怎么办"。**原型回答一个问题**。
- **别把逻辑和 TUI 揉一起**。reducer / 状态机里出现 `console.log`、prompt、terminal 转义码,它就不可移植了。**保持 TUI 是纯模块上的薄壳**。
- **别把 TUI 壳上生产**。壳是为"手动从 terminal 驱动"优化的。**它背后的逻辑模块才是值得留的东西**。
