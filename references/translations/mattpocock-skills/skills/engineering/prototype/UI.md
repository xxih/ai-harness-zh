# UI 原型

> 原文:[UI.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/prototype/UI.md)

在**同一路由**上生成**几种截然不同的 UI 变体**,通过浮动底栏切换。用户在浏览器里翻、挑一个(或从每个里偷一块),然后丢掉其余。

如果问题是逻辑/状态而不是长相——**错分支**,用 [LOGIC.md](LOGIC.md)。

## 什么时候是对的形状

- "这个页面该长啥样?"
- "我想在 commit 之前先看几个 dashboard 选项。"
- "试试设置界面的不同布局。"
- 任何用户否则就要花一天在脑子里在三个模糊 mockup 之间挑的时候。

## 两个子形状 —— 强烈偏好 A

UI 原型当它**贴着真应用其余部分**(真 header、真 sidebar、真数据、真密度)出现时**好判断得多**。**孤零零的一次性路由是真空**——每个变体单看都还行。**有合理的现有页面能挂的就走 A**。**只在原型真的没邻居可挂时才走 B**。

### 子形状 A —— 改造已有页面(首选)

路由已存在。**变体在同一路由上渲染**,由 `?variant=` URL 参数门控。**已有的数据 fetch、参数、auth 都保留**——只换渲染。**默认就是这个**,除非有具体理由不这么干。

如果原型是为某个"还没页面、但 *会自然住在某个页面里* 的东西"(dashboard 新区块、设置页新卡片、现有流程新步骤),**那也是 A**。把变体挂进宿主页面。

### 子形状 B —— 新页面(最后手段)

只在原型化的东西**真的没现有页面可住**时用——比如全新顶层表面,或没法合理嵌入任何地方的流程。

按项目已有路由约定建**一次性路由**——别发明新顶层结构。**起名让人一眼看出是原型**(比如路径或文件名含 `prototype`)。同样 `?variant=` 模式。

走 B 前**冷静检查**:真的没现有页面能嵌吗?**空路由会藏住设计问题,真页面会暴露它**。

两个子形状的**浮动底栏完全一致**。

## 流程

### 1. 写下问题 + 选 N

默认 **3 个变体**。多于 5 就不再"截然不同",开始变噪声——封顶。

把计划用一行写下来,放原型位置或文件顶端注释:

> "设置页的三个变体,通过 `?variant=` 在已有 `/settings` 路由上切换。"

**这无论用户在不在都成立**。

### 2. 生成"截然不同"的变体

起草每个变体。每个都受这些约束:

- 页面的目的 + 它能拿到的数据
- 项目的组件库 / 样式系统(TailwindCSS、shadcn、MUI、纯 CSS,等等)
- 清晰的导出组件名,如 `VariantA`、`VariantB`、`VariantC`

变体必须**结构上不同**——不同布局、不同信息层级、不同主要 affordance,**不只是不同颜色**。三个微调过的卡片网格不是 UI 原型,是壁纸。如果两个草稿太像,**用明确的"不要用卡片网格"指引重做一个**。

### 3. 接起来

在路由上建一个 switcher 组件:

```tsx
// 伪代码 —— 适配项目框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形状 A(现有页面):**把已有数据 fetch 都留在 switcher 上面**;只有渲染子树按变体变。

子形状 B(新页面):`/prototype/<name>` 下的一次性路由挂同一个 switcher。

### 4. 构浮动 switcher

屏幕底部居中的小固定栏,三部分:

- **左箭头** —— 循环到上一个变体(绕回)
- **变体标签** —— 显示当前变体 key,以及(如果变体导出了名字)变体名。例:`B — Sidebar layout`
- **右箭头** —— 循环到下一个

行为:

- 点箭头**更新 URL 参数**(用框架的 router —— Next 用 `router.replace`,React Router 用 `navigate`),变体可分享、刷新稳定。
- 键盘:`←` / `→` 也循环。**`<input>`、`<textarea>`、`[contenteditable]` 聚焦时不要拦截**箭头。
- 视觉上和页面**明显区分**(高对比胶囊、微阴影),让人一看就知道**它不是被评估的设计的一部分**。
- **生产构建中隐藏** —— 用 `process.env.NODE_ENV !== 'production'` 或等价检查门控,**防止失误合并把这个栏推到用户面前**。

把 switcher 放在**共享组件**里,两个子形状都复用。位置放在项目里共享 UI 该住的地方。

### 5. 交给用户

把 URL(和 `?variant=` 的 key)告诉用户。**他们什么时候有空什么时候翻**。有趣的反馈通常是 **"我想要 B 的 header + C 的 sidebar"**——**那才是他们真正想要的设计**。

### 6. 抓取答案 + 清理

某个变体胜出后,**写下哪个胜出 + 为什么**(commit、ADR、issue,或 AFK 时挨着原型的 `NOTES.md`)。然后:

- **子形状 A** —— 删失败变体 + switcher;把胜者折进已有页面
- **子形状 B** —— 把胜者升格为真路由,删一次性路由 + switcher

**别留变体组件或 switcher 在那烂着**。它们坏得快,会让下一个读者困惑。

## 反模式

- **只是颜色或文案不同的变体**。那是微调,不是原型。**真变体在结构上分歧**。
- **变体之间共享太多代码**。共享 `<Header>` OK,共享 `<Layout>` 就废了——**每个变体必须能自由扔掉 layout**。
- **把变体接真 mutation**。**只读原型很 OK**。要 mutate 的话,指到 stub——问题是"它该长啥样",不是"后端 work 不 work"。
- **把原型直接升级到生产**。变体代码是在**原型约束**下写的(无测试、最小错误处理)。**折进真代码时要重新写**。
