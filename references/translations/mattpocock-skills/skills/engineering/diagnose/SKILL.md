# Diagnose(诊断)

> 原文:[skills/engineering/diagnose/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/diagnose/SKILL.md)

一套对付难 bug 的纪律。只有在显式有理由时才能跳过某个阶段。

探索代码库时,用项目的领域术语表建立"相关模块的清晰心智模型",并查阅你正在动的那块区域的 ADR。

## Phase 1 — 建反馈环

**这一步才是真正的本事**。其它所有事情都是机械活。**只要你有一个快、确定、agent 可跑的"过 / 不过"信号,你就会找到原因**——二分、假设检验、加 log,都只是消费这个信号。如果没有这个信号,盯着代码看再久也没用。

在这一步**不成比例地多花精力**。**激进。富有创意。拒绝放弃。**

### 构造反馈环的若干方式 — 大致按下面顺序尝试

1. **失败测试**,在能命中 bug 的任意接缝处——单元、集成、e2e。
2. **Curl / HTTP 脚本**打跑着的 dev server。
3. **CLI 调用**配合 fixture 输入,把 stdout 和已知正确快照做 diff。
4. **Headless 浏览器脚本**(Playwright / Puppeteer)——驱动 UI,断言 DOM / console / network。
5. **回放抓到的 trace**。把真实的网络请求 / payload / 事件日志存盘,在隔离环境里通过代码路径回放。
6. **一次性测试架子**。最小化拉起系统的一个子集(单服务 + mock 依赖),用一次函数调用就触发到 bug 代码路径。
7. **Property / fuzz 循环**。如果 bug 是"有时输出错",就跑 1000 次随机输入找失败模式。
8. **二分架子**。如果 bug 出现在两个已知状态(commit、数据集、版本)之间,自动化"启到状态 X,检查,重复",这样你就能 `git bisect run`。
9. **差分循环**。同一份输入跑老版本 vs 新版本(或两种 config),diff 输出。
10. **HITL bash 脚本**(human-in-the-loop)。**最后手段**。如果必须有人来点,用 `scripts/hitl-loop.template.sh` 来"驱动那个人",让循环仍然有结构。抓到的输出反馈给你。

**构造对的反馈环,bug 已经修了 90%。**

### 在反馈环本身上迭代

把反馈环当成产品。一旦你有了"某个"环,就问:

- 能更快吗?(缓存 setup、跳过无关初始化、缩小测试范围。)
- 信号能更锐利吗?(对具体症状断言,而不是"没崩"。)
- 能更确定吗?(钉死时间、播种 RNG、隔离文件系统、冻结网络。)

30 秒的 flaky 环比没环只好一点。**2 秒的确定环是调试超能力**。

### 非确定性 bug

目标不是"干净复现",而是**更高的复现率**。把触发器循环 100 次、并行、加压、缩窄时序窗口、注入 sleep。50% flake 是可调的;1% 不行——把率拉到可调为止。

### 真的造不出环的时候

**停下,明说**。列出你试过的。问用户要:(a) 能复现的环境访问权,(b) 抓到的工件(HAR 文件、log dump、core dump、带时间戳的录屏),或 (c) 临时加生产 instrumentation 的许可。**不要**在没环的情况下进入假设阶段。

**没有可信的环之前,不要进入 Phase 2。**

## Phase 2 — 复现

跑反馈环。亲眼看 bug 出来。

确认:

- [ ] 反馈环产生的是**用户描述的那个**失败模式——不是附近碰巧也错的另一个失败。错的 bug = 错的修。
- [ ] 失败在多次运行间都可重现(非确定性 bug 则可重现到足以调试的频率)。
- [ ] 你已经抓到了精确症状(报错信息、错误输出、慢的耗时),这样后面阶段能验证修复是真的解决了它。

复现不出来就别往下走。

## Phase 3 — 提出假设

**在测试任何一个之前**,先生成 **3-5 个排好序的假设**。只想一个假设会把你锚定在第一个看似合理的想法上。

**每个假设必须可证伪**:说出它的预测。

> 格式:"如果 <X> 是原因,那么 <改 Y> 会让 bug 消失 / <改 Z> 会让它更严重"。

**说不出预测的假设就是脑补**——丢掉或锐化它。

**测试前把排好序的列表给用户看**。他们经常有领域知识能立刻重排("我们刚部署了对 #3 的改动"),或知道哪些假设已经被排除过了。一个便宜的 checkpoint,省时间巨多。**别因此阻塞**——用户不在的话按你的排序继续。

## Phase 4 — 加探针(Instrument)

每个探针必须对应 Phase 3 的某个具体预测。**一次只改一个变量。**

工具优先级:

1. **Debugger / REPL 直接检查**,如果环境支持。**一个断点胜过十条 log**。
2. **针对性 log**,加在能区分假设的边界上。
3. 永远不要"全 log + grep"。

**给每条 debug log 打唯一前缀**,例如 `[DEBUG-a4f2]`。结尾清理就是一次 grep。**没打 tag 的 log 会残留;打 tag 的 log 会被干掉**。

**性能分支**。对于性能回退,log 通常没用。改用:先建立 baseline 测量(timing harness、`performance.now()`、profiler、query plan),然后二分。**先测,再修**。

## Phase 5 — 修 + 回归测试

**先写回归测试再写修复**——但**仅当存在一个对的接缝**。

"对的接缝"是指:测试在 bug 实际发生的调用点处,演练**真实的 bug 模式**。如果可用的接缝太浅(bug 需要多调用方而测试只有单调用方;单元测试无法复制触发 bug 的链路),那里的回归测试会给你**假信心**。

**没有对的接缝本身就是一个发现**。记下来。**代码库的架构正在阻止这个 bug 被锁死**。把这一点交给下一个阶段。

如果有对的接缝:

1. 把最小化的复现变成那个接缝上的失败测试。
2. 看它失败。
3. 应用修复。
4. 看它通过。
5. 用 Phase 1 的反馈环对原始(未最小化的)场景重跑。

## Phase 6 — 清理 + 复盘

**声明完成前必须做完**:

- [ ] 原始复现不再复现(重跑 Phase 1 反馈环)
- [ ] 回归测试通过(或"没接缝"已被书面记录)
- [ ] 所有 `[DEBUG-...]` instrumentation 已移除(grep 那个前缀)
- [ ] 一次性原型已删除(或挪到清晰标记的 debug 位置)
- [ ] 最终被证明对的那个假设写在 commit / PR 信息里——这样下一个调试者能学到

**然后问:什么能阻止这个 bug 发生?** 如果答案涉及架构变更(没好的测试接缝、调用方缠绕、隐藏耦合),把具体问题交给 `/improve-codebase-architecture` skill。**这个建议要在修完之后再给**,不是之前——你现在拥有的信息比开始时多。
