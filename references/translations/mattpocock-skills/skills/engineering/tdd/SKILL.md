# Test-Driven Development(测试驱动开发)

> 原文:[skills/engineering/tdd/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md)

## 哲学

**核心原则**:测试应该通过**公共接口**验证**行为**,不是验证实现细节。代码可以全换,测试不该变。

**好测试**是集成风格:它通过公共 API 演练真实代码路径。它描述系统**做什么**,不是**怎么做**。一个好测试读起来像规格说明——"用户用合法购物车能结账"直接告诉你存在什么能力。这种测试在重构中存活,因为它不在乎内部结构。

**坏测试**和实现耦合。它 mock 内部协作方、测私有方法、或者通过外部手段验证(比如直接查数据库而不走接口)。**警告信号**:你重构时测试挂了,但行为没变。如果你重命名了一个内部函数测试就 fail,这些测试在测的是实现,不是行为。

例子见 [tests.md](tests.md),mock 规则见 [mocking.md](mocking.md)。

## 反模式:水平切片

**不要先写完所有测试,再写完所有实现**。这叫"水平切片"——把 RED 当成"写完所有测试"、GREEN 当成"写完所有代码"。

这会产出**烂测试**:

- 一次性大批量写的测试在测**想象中的**行为,不是**真实**行为
- 你会去测**形状**(数据结构、函数签名),而不是用户能感知的行为
- 测试对真实变更不敏感——行为坏了它通过,行为没事它失败
- 你跑得比车灯还快,在懂实现之前就把测试结构定死了

**正确做法**:用**示踪弹**做垂直切片。一个测试 → 一段实现 → 重复。每个测试都基于你从上一轮学到的东西。因为你刚写完代码,你正好知道哪种行为重要、怎么验证。

```
错(水平):
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

对(垂直):
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## 工作流

### 1. 规划

探索代码库时,用项目的领域术语表——这样测试名和接口词汇都和项目语言对齐——并尊重你正在动的区域的 ADR。

写任何代码前:

- [ ] 跟用户确认接口要怎么改
- [ ] 跟用户确认要测哪些行为(排优先级)
- [ ] 找[深模块](deep-modules.md)的机会(小接口 + 深实现)
- [ ] 为[可测试性](interface-design.md)设计接口
- [ ] 列要测的行为(不是实现步骤)
- [ ] 拿到用户对计划的批准

问:"公共接口应该长啥样?哪些行为最重要去测?"

**你不可能测所有东西**。跟用户确认哪些行为最关键。把测试精力放在关键路径和复杂逻辑上,不是每个可能的边界情况。

### 2. 示踪弹

写**一个**测试,确认系统的**一件**事:

```
RED:   写第一个行为的测试 → 失败
GREEN: 写最小代码让它过 → 通过
```

这就是你的示踪弹——证明这条路径端到端能通。

### 3. 增量循环

对每个剩余行为:

```
RED:   写下一个测试 → 失败
GREEN: 最小代码让它过 → 通过
```

规则:

- 一次一个测试
- 只写够让当前测试通过的代码
- **不要预判未来测试**
- 测试聚焦在可观测行为

### 4. 重构

所有测试通过后,找[重构候选](refactoring.md):

- [ ] 抽公共
- [ ] 加深模块(把复杂度藏到简单接口背后)
- [ ] 自然处应用 SOLID
- [ ] 想想新代码暴露出现有代码哪些问题
- [ ] 每次重构后跑测试

**RED 期间永远不要重构**。先到 GREEN。

## 每轮检查清单

```
[ ] 测试描述的是行为,不是实现
[ ] 测试只用公共接口
[ ] 测试能在内部重构中存活
[ ] 代码量对当前测试是最小的
[ ] 没有为未来加的投机功能
```
