# Agent Orchestration Templates

## 1. 角色选择速查

- `planner`
  - 用于范围不清、需要拆任务、需要决定顺序和边界
- `orchestrator`
  - 用于主控全局状态、调度子任务、回收结果、做 gate
- `worker`
  - 用于明确实现任务
- `explore`
  - 用于只读检索、盘点现状、找相似实现、查依赖和测试
- `reviewer`
  - 用于规格符合性、代码质量、风险和验证门禁

## 2. 并行独立性检查

只有大部分问题回答为“是”，才适合并行：

- 每个子任务是否有单独的目标和完成标准？
- 每个子任务是否可以在不读取其他子任务中间结果的情况下推进？
- 各子任务的主要写集是否基本不重叠？
- 是否不存在必须先做 A 才能做 B 的关键顺序依赖？
- 主 agent 是否能说明最终如何回收和合并这些结果？

只要以下任一项成立，优先串行：

- 共享同一关键文件或同一状态机
- 共享同一架构决策，且决策尚未确定
- 其中一个任务本质上只是另一个任务的前置分析
- 合并冲突成本会超过并行带来的收益

## 3. 单任务委派 Prompt 模板

```md
你现在只负责一个子任务。

## 任务

[一句话说明要解决的单个问题]

## 背景

- 当前总任务：[主任务]
- 相关模块/文件：[路径或模块名]
- 这项子任务在全局流程中的位置：[research / plan / execute / review / verify]

## 已知信息

- [事实 1]
- [事实 2]
- [事实 3]

## 非目标

- 不要处理 [无关范围 1]
- 不要修改 [无关模块 2]
- 不要自己扩展需求

## 预期输出

- [具体交付物 1]
- [具体交付物 2]

## 验证方式

- 需要提供哪些文件、diff、测试结果、命令输出或证据

## 阻塞上报

如果信息不足、范围冲突或发现更大的前置问题，不要自行扩展任务。
直接返回：
- 缺什么信息
- 为什么当前任务无法继续
- 建议主 agent 下一步补什么
```

## 4. 结果回收模板

主 agent 回收子任务结果时，至少检查：

1. 任务是否真的完成了
   - 不是只看摘要，而是看关键文件、diff 或证据
2. 是否有越界修改
   - 是否改了未授权的范围
3. 是否可被主线采纳
   - 是否需要返工、追问、重派或升级
4. 是否有 fresh verification evidence
   - 至少要有新的测试、检查、审阅或可验证证据

推荐记录格式：

```md
### 子任务：<name>

- 角色：planner / worker / explore / reviewer
- 状态：accepted / follow-up / re-dispatch / blocked
- 结果摘要：...
- 验证证据：...
- 下一步动作：...
```
