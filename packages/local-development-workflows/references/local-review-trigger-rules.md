# Local Review 触发规则

这份文档定义“什么时候必须做 local review，什么时候可以不做”，避免把 review 变成全靠当场感觉的动作。

这里的 local review 指本地独立质量评审，主要对应 `quality-review`，不是 GitHub 上的远端 PR review。

## 目标

- 给 local review 一个稳定触发条件
- 避免所有改动都被一刀切升级成重评审
- 也避免高风险改动在没有独立审视的情况下直接进入收尾

## 默认规则

默认不是“每次改动都必须 local review”，而是：

- 命中触发条件：必须做 local review
- 不命中触发条件：允许 `self-review + verify` 直接进入 finish / PR

## 必触发场景

以下任一命中，就应触发 local review：

### 1. 架构改动

例如：

- 模块边界调整
- 共享抽象提取
- 依赖方向变化
- 状态管理方式变化
- 存储、缓存、鉴权、并发模型调整

原因：

- 这类改动很容易“局部看起来合理，整体却退化”

### 2. 跨多个模块的耦合改动

例如：

- 同时改动多个 package
- 同时改动核心业务层、接口层、测试层
- 一次改动穿过多层调用链

原因：

- 这类改动的回归风险通常来自交界处，不来自单点代码

### 3. 高风险 bugfix

例如：

- 线上故障修复
- 数据一致性问题
- 权限 / 安全问题
- 并发 / 时序问题
- 很难通过肉眼穷尽边界的问题

原因：

- 修复本身可能对，但副作用容易漏

### 4. 大 diff

例如：

- 文件数明显偏多
- 单文件改动量明显偏大
- 改动已经超出“reviewer 可以快速完整扫完”的体量

建议：

- 优先先拆小；拆不小时，再做 local review

### 5. 测试表达不足但行为变化明显

例如：

- 虽然补了测试，但还无法清楚表达真实行为边界
- 有大量 mock，真实行为覆盖不足
- 改动影响路径比测试显式覆盖的更大

原因：

- 这类改动即使 verify 通过，也可能只是“证据不够强”

### 6. 合并前总审

适用于：

- 一个较大任务收尾前
- 一轮连续修改累计下来已形成较大变更面

原因：

- 前面每一步都没出问题，不代表整体集成后没有遗漏

## 可不触发场景

以下场景通常可以不单独做 local review，但仍应完成认真自审和 fresh verify：

### 1. 极小改动

例如：

- 纯文案修正
- 明确无行为变化的小范围重命名
- 注释、README、路径说明更新

### 2. 单点、低风险、小 diff 改动

例如：

- 单文件内的小 bugfix
- 改动面清楚、边界明确
- 测试表达已经足够直接

### 3. 机械性改动

例如：

- 规则一致的批量替换
- 已被现有测试充分覆盖的 API 改名
- 明显不涉及设计判断的格式或拼装修正

前提：

- 必须真的低风险、可机械验证
- 不是“表面机械，实则影响行为”

## 触发后最小要求

一旦触发 local review，至少要满足：

1. 明确评审对象
   - 本轮改了什么
   - 原本应该满足什么
2. 独立审视
   - 优先让独立 reviewer 看
   - 环境不支持时，再退回自审
3. 问题分级
   - Critical：必须先修
   - Important：原则上继续前先修
   - Minor：可记录后处理
4. 重新 verify
   - 修完 review 问题后，再做 fresh verification

## 不要触发的伪信号

以下理由不应该单独触发 local review：

- “我有点不安心”
- “看起来好像不少”
- “反正 review 一下总没坏处”
- “这是习惯动作”

这些都太模糊。要么命中稳定条件，要么不触发。

## 不做 local review 时的底线

即使本轮不触发 local review，也不等于可以跳过质量动作。

至少仍应做到：

- 一次认真自审
- 一次 fresh verify
- 进入 finish 前确认当前出口

## 与远端 PR review 的关系

- local review 解决的是“本地先做独立质量判断”
- PR review 解决的是“远端协作审批与评论线程”

二者不是互相替代关系。

推荐原则：

- 高风险改动：`local review + PR review`
- 小改动：`self-review + verify + PR review`

不要把所有任务都升级成“双 review 串行”。
